## 2. Исправление трёх багов из §12

### 2.1 Баг 1: кнопка `?????????` — моё предположение было неверным

**Файл:** `app/lib/profile/edit_carrier_profile1/edit_carrier_profile1_widget.dart`

Исходная проблема (подтверждена скриншотом пользователя): на экране «Ваши
данные» кнопка подписана `?????????`, а диалог — `?????? ?????????`. Это не
заглушки разработчика, а **потерянная кириллица** при экспорте из FlutterFlow.

**Здесь важное признание.** В предыдущем документе (§12.1) я написал, что по
смыслу окружающего кода это восстанавливается как «Удалить аккаунт». Прежде чем
править, я прочитал обработчик — и предположение оказалось **ложным**:

```dart
// edit_carrier_profile1_widget.dart:538-562 — фактический обработчик
await currentUserReference!.update(createUsersRecordData(
  // ... поля профиля
));
```

Кнопка вызывает `update` на профиле пользователя. Это кнопка **сохранения**, а не
удаления. Если бы я правил «по документу», не перечитав код, я бы подписал кнопку
сохранения словом «Удалить аккаунт» — то есть создал бы баг заметно опаснее
исходного: пользователь боялся бы нажать кнопку, которая сохраняет его данные,
либо нажимал бы её, ожидая удаления аккаунта.

Реконструкция подтверждается подсчётом символов:

| В коде | Знаков `?` | Восстановлено | Букв |
|---|---|---|---|
| `'?????????'` | 9 | `'Сохранить'` | 9 |
| `'?????? ?????????'` | 6 + 9 | `'Данные сохранены'` | 6 + 9 |

Строки заведены не хардкодом, а в систему локализации — как остальные строки
приложения:

```dart
// app/lib/flutter_flow/internationalization.dart
// Восстановлено: в экспорте FlutterFlow строки потерялись и превратились
// в '?????????' / '?????? ?????????' — кириллица не выжила кодировку.
"ecp1save": {"ru": "Сохранить", "en": "Save"},
"ecp1saved": {"ru": "Данные сохранены", "en": "Data saved"}
```

**Вывод на будущее:** потерянные строки нельзя восстанавливать по смыслу
окружающего текста — только по фактическому обработчику. В экспорте FlutterFlow
таких строк может быть больше; каждую нужно проверять отдельно.

### 2.2 Баг 2: валидаторы пропускали мусор — масштаб оказался шире

В §12.2 был описан один файл — `fill_profile_carrier_model.dart`, где проверка
сводилась к `isEmpty` и `length < 3`, из-за чего строка `abc` проходила как номер
перевозчика.

При обходе всех форм выяснилось, что **дилерские модели не имели даже такой
проверки**:

```dart
// fill_profile_diller_model.dart — было
String? _dillerNumberValidator(BuildContext context, String? val) {
  if (val == null || val.isEmpty) {
    return 'Обязательное поле';
  }
  return null;   // ← ни длины, ни формата: '1' и '???' проходят
}
```

Итого валидация подключена в **четыре** модели:

| Модель | Поля | Было |
|---|---|---|
| `fill_profile_carrier_model.dart` | компания, номер перевозчика, права | `isEmpty` + `length < 3` |
| `edit_carrier_profile1_model.dart` | компания, номер перевозчика, права | `isEmpty` + `length < 3` |
| `fill_profile_diller_model.dart` | лицензия дилера, права | только `isEmpty` |
| `edit_diller_profile1_model.dart` | лицензия дилера, права | только `isEmpty` |

Валидаторы вызываются делегированием, чтобы правило существовало в одном месте:

```dart
String? _carrierNumberTextControllerValidator(BuildContext context, String? val) =>
    DocumentValidators.carrierNumber(val);
```

### 2.3 Баг 3: фильтр `[0-9]` — не одно место, а восемь

В §12.3 указан один файл, что создавало впечатление единичного дефекта.
`grep` по репозиторию нашёл **18 вхождений** `RegExp('[0-9]')`. Каждое я
классифицировал, найдя ближайший `*TextControllerValidator`:

**Исправлено (8 полей — поля документов):**

| Экран | Поля |
|---|---|
| `fill_profile_carrier_widget.dart` | номер перевозчика (~323), права (~425) |
| `fill_profile_diller_widget.dart` | лицензия дилера (~226), права (~323) |
| `edit_carrier_profile1_widget.dart` | номер перевозчика (~387), права (~528) |
| `edit_diller_profile1_widget.dart` | лицензия дилера (~245), права (~344) |

**Намеренно оставлено числовым (10 вхождений):** телефон, цена, даты, фильтры
поиска, `currency_text_input_formatter.dart`. Там фильтр только цифр корректен —
менять его было бы вредом, а не исправлением. В частности, в
`edit_diller_profile1_widget.dart:526` поле `takeDate` осталось числовым
сознательно, хотя находится в том же файле, где две правки.

Проверка результата счётом:

```
до исправления (cebf328): 18 вхождений
после (c74d79f):          10 вхождений
разница:                   8  ← ровно поля документов
```

Общие форматтеры вынесены в один файл, чтобы не размножать копии:

```dart
/// КРИТИЧНО: не заменять на `[0-9]` — права США почти во всех штатах
/// содержат букву (CA D1234567, FL A123456789012).
final documentNumberFilter =
    FilteringTextInputFormatter.allow(RegExp(r'[A-Za-z0-9-]'));

class UpperCaseTextFormatter extends TextInputFormatter { /* ... */ }

const documentNumberFormatters = <TextInputFormatter>[UpperCaseTextFormatter()];
```

Комментарий-предупреждение здесь не декоративный: следующий экспорт из
FlutterFlow может снова перезаписать поля фильтром `[0-9]`, и человеку, который
будет разбираться, нужна причина, а не только правило.

Во всех 8 полях также заменён `keyboardType: TextInputType.number` на
`TextInputType.text` — иначе на телефоне открывалась цифровая клавиатура без
букв, и поле оставалось непригодным даже с исправленным фильтром.

## 3. Новый файл: `document_validators.dart`

**Путь:** `app/lib/custom_code/document_validators.dart`

Файл намеренно **не зависит** от эталонного модуля `verification/` — только от
`package:flutter/services.dart`. Причина: модуль `verification/` — это отдельное
демо-приложение со своим `pubspec.yaml`; импортировать его в продакшн нельзя, а
копировать его целиком ради пяти функций — избыточно. Поэтому валидаторы
перенесены в компактной самодостаточной форме.

| Метод | Правило |
|---|---|
| `carrierNumber` | USDOT: 4–8 цифр без ведущего нуля; либо MC с префиксом `MC` |
| `driverLicense` | буквы+цифры, 5–20 знаков, минимум одна цифра |
| `dealerLicense` | буквы+цифры, 4–20 знаков, минимум одна цифра |
| `companyName` | 2–120 знаков, обязательно содержит буквы |
| `vin` | 17 знаков, без `I/O/Q`, контрольная цифра по ISO 3779 |

Требование «минимум одна цифра» отсекает случай, когда пользователь вписывает в
поле номера слово (`abcdef` формально проходит по «буквы+цифры, 5–20»).

Валидаторы проверяют **только формат** — это первый уровень модели доверия из
предыдущего документа. Формат не подтверждает, что документ существует; для
этого нужна проверка в реестре FMCSA (уровень `registry`), и только она даёт
публичный бейдж.

## 4. Страховка при отправке машины

Запрос пользователя: «при отправке машины нужно предлагать оплатить страховку».

### 4.1 Почему момент выбран именно такой

Момент отправки — это `onAccept` в `deal_responses_widget.dart`: дилер принимает
отклик перевозчика, сделка переходит в `DealStatus.InConfirm`, и машина
физически передаётся другому человеку.

Почему не на этапе создания заказа:

1. **Перевозчик ещё не известен.** На создании заказа некому считать тариф.
2. **Тариф зависит от того, КОМУ отдают машину.** Физлицо без коммерческого
   покрытия — заметно более высокий риск, чем компания с действующим FMCSA
   authority. Считать премию до выбора перевозчика бессмысленно.
3. **Это последняя точка, где решение ещё что-то меняет.** После передачи машины
   страховать уже нечего.

### 4.2 Что уже было в коде

Важное открытие: функциональность **наполовину существует**.

В `deals_record.dart` уже есть шесть полей (строки 148–176):

```dart
insurance_required   // bool
insurance_quote_id   // String
insurance_provider   // String
insurance_premium    // int — в центах, не в долларах
insurance_policy_id  // String
insurance_policy_url // String
```

А в `create_deal7_comp_widget.dart` есть чекбокс страховки, но расчёт в нём —
задокументированная пустышка:

```dart
Future<void> _calculateInsuranceQuote(String? dealId) async {
  if (dealId == null) return;   // ← на этапе создания dealId всегда null
  // ...
}
```

То есть автор кода уже столкнулся с проблемой из §4.1 и оставил заглушку. Моя
реализация решает ровно её — переносит расчёт в момент, когда `dealId` и
перевозчик уже известны.

Поле `insurance_premium` хранится **в центах** (`int`). Это важно: при
отображении нужно делить на 100, а не выводить как доллары. Такую ошибку легко
допустить, и она даст цену в 100 раз выше.

### 4.3 Логика виджета и контракт возврата

**Новый файл:** `app/lib/components/insurance_offer_bottom_widget.dart`

```dart
InsuranceOfferBottomWidget({
  required DocumentReference dealRef,
  required String carName,
  required int price,
  bool carrierIsIndividual = false,
  bool carrierHasOwnInsurance = false,
})
```

Поток: `initState` → `_loadQuote()` (Cloud Function `calculateInsuranceQuote`) →
показ премии → либо `_purchase()` (`purchaseInsurance`), либо
`_declineWithConfirm()`.

**Контракт возврата — три различных состояния, а не два:**

| Возврат | Значение | Действие вызывающего кода |
|---|---|---|
| `{'insured': true, 'quote': {...}}` | оплачено | отправлять, записать полис |
| `{'insured': false}` | **осознанный** отказ | отправлять без страховки |
| `null` | лист закрыт без решения | **не отправлять** |

Различие между `{'insured': false}` и `null` — принципиальное. Если бы закрытие
листа трактовалось как отказ, дилер, случайно смахнувший панель, отправил бы
машину без страховки, не приняв решения. Поэтому лист защищён:

```dart
isDismissible: false,
enableDrag: false,
```

а отказ требует подтверждения в отдельном `AlertDialog`. Отказаться можно —
но не случайно.

Текст предупреждения о риске выбирается из трёх вариантов по состоянию
перевозчика (`_riskNotice()`): у перевозчика есть своё покрытие / перевозчик —
физлицо / нейтральный случай. Отдельный текст для физлица нужен потому, что
личный автополис почти всегда содержит исключение для коммерческого
использования (`for hire`) — то есть настоящий полис перевозчика может не
покрыть платную перевозку чужой машины.

Оформление — в утверждённом стиле приложения: жёлтая палитра
(`#FAE28C` primary), пилюля-кнопка `borderRadius: 28`, предупреждающий блок
на `#FFF6E5` с рамкой `#F0D089` и текстом `#B26A00`/`#7A4A00`.

### 4.4 Встраивание в `onAccept`

```dart
// deal_responses_widget.dart
final insuranceResult = await _offerInsurance(
  myResponse: myResponse,
  price: (confirmData['price'] as num?)?.toInt() ?? widget.deal?.price.toInt() ?? 0,
);
// null — дилер закрыл лист, не приняв решения: отправку не начинаем.
if (insuranceResult == null) return;

// ... формирование data со статусом InConfirm ...

data['insurance_required'] = insuranceResult['insured'] == true;
final quote = insuranceResult['quote'] as Map<String, dynamic>?;
if (quote != null) {
  data.addAll(quote);
}
await widget.deal?.reference.update(data);
```

Реквизиты полиса пишутся **в той же операции**, что и смена статуса. Иначе
возможно расхождение: страховка оплачена, а в заказе не отражена — при сбое между
двумя записями деньги списаны, а полиса в сделке нет.

Чтение профиля перевозчика обёрнуто в `try/catch` с пустым обработчиком —
осознанно:

```dart
} catch (_) {
  // Не удалось прочитать профиль — показываем нейтральный текст.
  // Само предложение страховки при этом не скрываем.
}
```

Недоступность профиля влияет только на **текст предупреждения**. Скрывать из-за
этого само предложение страховки нельзя — это отняло бы у дилера возможность
застраховать перевозку из-за сетевой ошибки.

Отсутствующий `carrier_kind` трактуется как `company` — это то же решение об
обратной совместимости, что описано в предыдущем документе: миграция базы не
требуется.

## 5. Три тестовых аккаунта

Запрошены три аккаунта: дилер, перевозчик-компания, перевозчик-физлицо.

**Задача не выполнена, и вот почему.** Создание пользователей в Firebase Auth
требует Admin SDK-ключа:

```
$ ls /opt/flutter/ | grep -iE "firebase|adminsdk|google-services"
NO FIREBASE CONFIG
```

Ключа в песочнице нет. Без него нельзя ни создать пользователя в Auth, ни
записать профиль в Firestore. Обойти это невозможно — и я не буду делать вид,
что аккаунты созданы.

Чтобы задача не осталась пустой, в репозиторий добавлен готовый к запуску скрипт
[`scripts/create_test_accounts.py`](../scripts/create_test_accounts.py). Он
создаёт ровно три аккаунта с корректными для схемы полями:

| Роль | поле `type` | `carrier_kind` | Документы |
|---|---|---|---|
| Дилер | `Diller` | — | `diller_license`, `dealer_license_number`, `dealer_license_state` |
| Перевозчик-компания | `Carrier` | `company` | `carrier_number`, `dot_number`, `company_legal_name` |
| Перевозчик-физлицо | `Carrier` | `individual` | `carrier_driver_license`, без DOT |

Уточнение по схеме: роль хранится в поле **`type`**, а не `user_type` — это
видно в `users_record.dart:222` (`deserializeEnum<UserType>(snapshotData['type'])`).
Имена полей в скрипте выверены по этому файлу, а не предположены по смыслу.

Аккаунты создаются **неверифицированными** (`verification_status: 'idle'`,
`verified: false`) намеренно. Выставить `verified: true` было бы удобнее для
тестов, но это дало бы бейдж без реальной проверки в реестре и создало ложное
представление о работе модели доверия. Номера документов синтаксически валидны,
но заведомо отсутствуют в FMCSA.

Запуск (после загрузки ключа в Firebase-вкладку):

```bash
pip install firebase-admin==7.1.0
python3 scripts/create_test_accounts.py
```

Скрипт идемпотентен: повторный запуск не создаёт дубли, а обновляет профили.

**Что нужно от вас:** загрузить `firebase-admin-sdk.json` (Firebase Console →
Project settings → Service accounts → язык **Python** → Generate new private
key). После этого аккаунты создаются одной командой.

## 7. Нерешённое и риски

### 7.1 Cloud Functions не существуют

Виджет вызывает две функции, которых **нет на сервере**:

| Функция | Статус |
|---|---|
| `calculateInsuranceQuote` | вызывается существующим кодом, но серверной части нет |
| `purchaseInsurance` | придумана мной, серверной части нет |

Каталога `functions/` в корне репозитория нет вообще. Пока функции не написаны,
UI страховки будет показывать ошибку загрузки расчёта. Это ожидаемое поведение,
не регрессия — но и «готовой страховкой» это называть нельзя.

Ожидаемый контракт: `calculateInsuranceQuote({dealId})` → `{cost, quoteId,
provider}`, где `cost` — центы; `purchaseInsurance({dealId, quoteId})` →
`{policyId, policyUrl}`.

### 7.2 Конфликт версий зависимостей

`flutter pub get` в песочнице не проходит без правки пинов. Решать нужно
осознанно: либо поднять `collection`/`intl` в репозитории (затронет всю команду),
либо зафиксировать версию Flutter, под которую сделан экспорт. Я оставил пины
как есть.

### 7.3 Два места принятия решения о страховке

Теперь страховка предлагается в двух точках: старый чекбокс при создании заказа
(нерабочий) и новый лист при отправке. Их нужно согласовать — иначе дилер может
отметить чекбокс при создании и получить второй вопрос при отправке. Мой
вариант: превратить чекбокс в отметку «планирую застраховать», а оплату оставить
только в момент отправки.

### 7.4 Страховка остаётся самым слабым уровнем доверия

Об этом подробно в предыдущем документе, но повторю применительно к оплате:
реестра полисов не существует. Даже оплаченный полис нужно проверять на предмет
покрытия платной перевозки чужого автомобиля (`non-owned auto liability`).
Флаг `insurance_required: true` в сделке означает «оплачено через нас», а не
«риск закрыт».

## Итог

Три бага из §12 исправлены и проверены тестами. Страховка при отправке машины
реализована на стороне приложения и компилируется, но требует двух Cloud

предыдущий отчёт содержал уверенное, но ошибочное утверждение. Если бы я правил
код по документу, не перечитав обработчик, кнопка сохранения получила бы подпись
«Удалить аккаунт». Документ полезен как карта, но проверять нужно по коду.
