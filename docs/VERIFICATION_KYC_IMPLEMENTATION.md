<a name="1"></a>
## 1. Зачем это вообще нужно: постановка проблемы

Изначальный вопрос был сформулирован так: *«все поля с номерами документов и лицензий,
и у перевозчика, и у дилера, должны иметь мгновенную валидацию с автозаполнением из
реальных реестров»*.

За этой формулировкой стоит вполне конкретная бизнес-проблема. На маркетплейсе
автоперевозок есть три стороны, и каждая рискует деньгами:

* **Дилер** отдаёт автомобиль стоимостью $20–80k незнакомому человеку.
* **Перевозчик** тратит топливо и время, рассчитывая на оплату.
* **Платформа** отвечает репутацией и, в США, вполне реальными судебными исками.

Если единственная проверка — «пользователь ввёл номер и загрузил фото» — платформа
де-факто не проверяет ничего. Поле `USDOT` из 7 цифр можно придумать за секунду.
Поэтому задача разбивается на две независимые:

| Задача | Что решает | Где выполняется |
|---|---|---|
| **Валидация формата** | Отсекает опечатки и явную ерунду, экономит вызовы платных API | На устройстве, бесплатно, мгновенно |
| **Проверка в реестре** | Отвечает на вопрос «этот номер существует и принадлежит именно этой компании?» | Внешний API, деньги/квоты, секунды |

Смешивать их нельзя. Именно из этого разделения выросла схема уровней доверия.

### Что было в продакшне до работ

Изучен реальный код репозитория (`app/lib/auth/fill_profile_carrier/`). Валидация
номера перевозчика на момент анализа:

```dart
// app/lib/auth/fill_profile_carrier/fill_profile_carrier_model.dart:39-55
String? _carrierNumberValidator(BuildContext context, String? val) {
  if (val == null || val.isEmpty) return 'Обязательное поле';
  if (val.length < 3) return 'Слишком короткий номер';
  return null;
}
```

То есть `abc` — валидный номер перевозчика. Это и есть точка, с которой начиналась работа.

## 2. Ключевое решение: четыре уровня доверия

Главная архитектурная идея всей работы. Статус «проверено» — не булево значение.
Есть **четыре качественно разных уровня**, и путать их — значит вводить в заблуждение
пользователей платформы.

```dart
// lib/models/verification.dart
enum VerificationTier {
  format,    // проверено математикой на устройстве
  registry,  // подтверждено государственным реестром
  provider,  // подтверждено сторонним KYC-провайдером
  manual,    // проверено человеком-модератором
}
```

### Что означает каждый уровень

| Уровень | Кто подтвердил | Стоимость | Даёт публичный бейдж? | Пример |
|---|---|---|---|---|
| `format` | Алгоритм на телефоне | $0 | **Нет** | VIN прошёл контрольную сумму ISO 3779 |
| `registry` | FMCSA, NHTSA — госреестр | $0 (публичные API) | **Да** | USDOT 80806 → «FEDEX FREIGHT INC», статус ACTIVE |
| `provider` | Stripe Identity, Checkr | $1.50–$10 | **Нет** (отдельный бейдж) | Селфи + водительское сверены биометрией |
| `manual` | Модератор DTD | зарплата | **Нет** | Скан дилерской лицензии Калифорнии |

### Почему только `registry` даёт бейдж «Проверено»

Это принципиально. Формат — не доказательство: контрольная сумма VIN лишь означает,
что цифры согласованы между собой, а не что машина существует. Модерация — оценочное
суждение сотрудника, а не факт. Только госреестр отвечает на вопрос
«эта организация существует, активна и называется именно так».

Реализовано на уровне типов, а не соглашений в коде:

```dart
extension VerificationStatusX on VerificationStatus {
  /// Бейдж «Проверено» даёт ТОЛЬКО подтверждение реестром.
  bool get grantsBadge =>
      this == VerificationStatus.verified && tier == VerificationTier.registry;
}
```

Тест, фиксирующий это как контракт (`test/widget_test.dart`):

```dart
test('только registry-verified даёт бейдж', () { ... });
```

### Восемь статусов вместо двух

```dart
enum VerificationStatus {
  idle,             // пользователь ещё не начал вводить
  checking,         // запрос в реестр в полёте (спиннер в поле)
  verified,         // подтверждено
  needsReview,      // формат верный, ушло на модерацию
  pendingProvider,  // ждём вебхук от KYC-провайдера (минуты-часы)
  invalidFormat,    // ошибка формата — исправляемая пользователем
  notFound,         // формат верный, но в реестре нет
  mismatch,         // в реестре есть, но данные расходятся
  unavailable,      // реестр недоступен — НЕ вина пользователя
}
```

Три статуса здесь неочевидны и заслуживают объяснения.

**`unavailable` — не блокирует отправку формы.** Если FMCSA лежит (а он лежит
регулярно, особенно по выходным), пользователь не должен застрять в регистрации.
Форма отправляется, номер уходит на отложенную перепроверку.

```dart
bool get allowsSubmit =>
    this == VerificationStatus.verified ||
    this == VerificationStatus.needsReview ||
    this == VerificationStatus.pendingProvider ||
    this == VerificationStatus.unavailable ||   // ← реестр упал, не вина юзера
    this == VerificationStatus.idle;
```

**`mismatch` vs `notFound`.** Совершенно разные сценарии для модератора.
`notFound` — скорее всего опечатка. `mismatch` («DOT существует, но принадлежит
другой компании») — либо ошибка, либо попытка присвоить чужую авторитетность.
Второе требует внимания человека.

**`pendingProvider` vs `checking`.** `checking` живёт секунды и умирает при закрытии
приложения. `pendingProvider` живёт часами, приходит вебхуком и должен переживать
перезапуск приложения. Это состояние в Firestore, а не в памяти виджета.

<a name="3"></a>
## 3. Третий тип пользователя: почему НЕ третий `UserType`

Задача: *«добавь ещё 3-й вариант пользователей — физ. лицо, тоже с проверкой KYC»*.

### Соблазнительное и неверное решение

```dart
enum UserType { Diller, Carrier, Individual }  // ❌ так делать нельзя
```

Перед реализацией был проведён анализ существующего кода. Результат:

* `UserType.Diller` проверяется в **14 местах** — ветвления UI, доступ к экранам, роутинг;
* `UserType.Carrier` — в **3 местах**;
* плюс запросы Firestore с фильтром `where('type', '==', ...)`.

Добавление третьего значения означает ревизию всех 17 ветвлений плюс миграцию
запросов. При этом каждое такое ветвление — потенциальный `else`, в который
новый тип провалится молча и неправильно.

### Принятое решение: разделение роли и способа проверки

Ключевое наблюдение: **физлицо-перегонщик — это не новая роль на маркетплейсе.**
Он делает буквально то же, что и компания-перевозчик: берёт заказ, везёт машину,
получает деньги. Отличается только *то, как платформа подтверждает, что ему можно доверять*.

Компанию проверяет FMCSA. Физлицо проверять в FMCSA нельзя — у него нет и не может
быть USDOT-номера. Значит, различие лежит не в роли, а в **пути верификации**.

Отсюда — три независимых поля вместо одного перегруженного:

```dart
// lib/models/user_kind.dart

/// РОЛЬ на маркетплейсе остаётся прежней: физлицо — это тот же Carrier.
/// type: UserType.Carrier

/// ПУТЬ ВЕРИФИКАЦИИ — новое поле.
enum CarrierKind { company, individual }

/// КАКИМ МЕТОДОМ подтверждён — производное, но хранится явно для аналитики.
enum VerificationMethod { fmcsa, identity }
```

### Обратная совместимость обеспечена дефолтом

Критично для существующей базы: у уже зарегистрированных перевозчиков поля
`carrier_kind` в документе просто нет. Читаем так:

```dart
extension CarrierKindX on CarrierKind {
  static CarrierKind fromFirestore(String? v) =>
      v == 'individual' ? CarrierKind.individual : CarrierKind.company;
      //                                          ↑ всё, что не 'individual',
      //                                            включая null → company
}
```

Миграция базы **не требуется**. Ни один существующий перевозчик не сломается.
Это зафиксировано тестом:

```dart
test('carrier_kind по умолчанию company — обратная совместимость', () {
  expect(CarrierKindX.fromFirestore(null), CarrierKind.company);
});
```

### Выигрыш

| | Третий `UserType` | `carrier_kind` |
|---|---|---|
| Правок в существующих ветвлениях | ~17 | 0 |
| Миграция Firestore | нужна | не нужна |
| Риск молчаливого падения в `else` | высокий | отсутствует |
| Фильтр дилера «только компании» | новый запрос | `where('carrier_kind','==','company')` |

Последняя строка — важное продуктовое следствие. Дилеру, который возит новые
автомобили и не готов доверять их физлицу, нужен фильтр. С предложенной схемой
это один предикат к существующему запросу.

<a name="4"></a>
## 4. Схема данных в Firestore

Поля, добавляемые к документу пользователя. Все — опциональные, все имеют
безопасный дефолт.

```jsonc
{
  // — существующее, НЕ меняется —
  "type": "Carrier",                    // роль на маркетплейсе

  // — новое: путь верификации —
  "carrier_kind": "individual",         // company | individual;  null → company
  "verification_method": "identity",    // fmcsa | identity

  // — результаты проверок; структура одинакова для всех полей —
  "verification": {
    "usdot": {
      "status": "verified",
      "tier": "registry",
      "value": "80806",
      "normalized": "80806",
      "registry_payload": {             // снимок ответа реестра на момент проверки
        "legalName": "FEDEX FREIGHT INC",
        "allowedToOperate": "Y",
        "statusCode": "A"
      },
      "checked_at": "2026-08-27T21:00:00Z",
      "source": "fmcsa"
    },
    "identity_verified":  { "status": "pendingProvider", "tier": "provider", "source": "stripe_identity" },
    "insurance_verified": { "status": "needsReview",     "tier": "manual"   },
    "mvr_verified":       { "status": "idle" },
    "background_verified":{ "status": "idle" }
  }
}
```

Три решения по схеме, которые стоит отметить.

**`registry_payload` хранится целиком.** Ответ реестра — это доказательство на
момент проверки. Компанию могут лишить authority через месяц; нужно уметь показать,
что на момент верификации статус был ACTIVE. Плюс это позволяет перепроверять
задним числом без повторного вызова API.

**`tier` хранится рядом со `status`.** Иначе невозможно отличить `verified`,
полученное из реестра, от `verified`, поставленного модератором вручную —
а это, как показано выше, разные вещи.

**Ключи слоёв KYC вынесены в перечисление**, чтобы имена полей не разъехались
между клиентом и Cloud Functions:

```dart
extension KycLayerX on KycLayer {
  String get fieldKey => switch (this) {
    KycLayer.identity      => 'identity_verified',
    KycLayer.drivingRecord => 'mvr_verified',
    KycLayer.criminal      => 'background_verified',
    KycLayer.insurance     => 'insurance_verified',
  };
}
```

<a name="5"></a>
## 5. Слои KYC для физлица и их стоимость

Для компании достаточно одной проверки — FMCSA возвращает и название, и статус
authority, и наличие страховки. Для физлица такого единого источника не существует.
Проверка распадается на четыре независимых слоя.

```dart
enum KycLayer { identity, drivingRecord, criminal, insurance }
```

| Слой | Что проверяем | Провайдер | Цена | Обязателен на старте |
|---|---|---|---|---|
| `identity` | Личность: селфи + документ, биометрическое сличение | Stripe Identity | **~$1.50** | **Да** |
| `insurance` | Полис ОСАГО-аналога с покрытием non-owned auto | Ручная модерация | $0 + время | **Да** |
| `drivingRecord` | MVR — история нарушений, действительность прав | Checkr | **~$10.00** | Нет, 2-й этап |
| `criminal` | Криминальный фон | Checkr | ~$10–30 | Нет, 2-й этап |

Приоритеты закодированы, а не описаны в комментарии:

```dart
bool get requiredAtLaunch => switch (this) {
  KycLayer.identity      => true,
  KycLayer.insurance     => true,
  KycLayer.drivingRecord => false,
  KycLayer.criminal      => false,
};
```

### Почему страховка — самый слабый и самый важный слой

Это главный риск всей затеи с физлицами, и его нужно понимать явно.

**Реестра страховых полисов, доступного приложениям, не существует.** Ни в одном
штате. Проверить полис программно нельзя — только глазами модератора по скану,
либо звонком в страховую.

Хуже другое. Личный автополис физлица, как правило, **не покрывает управление
чужим автомобилем за плату**. Это исключение прописано практически во всех
стандартных полисах США: «commercial use» / «for hire» exclusion. То есть
человек может добросовестно предъявить действующий полис — и всё равно не быть
застрахованным в момент перегона дилерского автомобиля.

Нужен отдельный продукт — **non-owned auto liability**. Это отражено в модели
как отдельный флаг, и его отсутствие даёт `mismatch`, а не `needsReview`:

```dart
Future<VerificationResult> submitInsurance({
  required bool fileAttached,
  required bool nonOwnedCoverage,
}) async {
  if (!fileAttached) {
    return VerificationResult.invalidFormat('Приложите скан полиса');
  }
  if (!nonOwnedCoverage) {
    // НЕ needsReview: личный полис без non-owned покрытия не годится
    // для перегона чужого автомобиля за плату. Это расхождение по сути,
    // а не вопрос к модератору.
    return VerificationResult.mismatch(
      'Личный полис не покрывает перегон чужого авто за плату. '
      'Нужен non-owned auto liability.',
    );
  }
  return VerificationResult.needsReview('Полис на проверке модератором');
}
```

### Правило допуска к заказам

Доступ открывается, только когда закрыты **все** слои, обязательные на старте.
Логика вынесена в чистую функцию — её легко тестировать и невозможно случайно
обойти в UI:

```dart
static ({bool allowed, String label, String reason}) resolveIndividualAccess(
  Map<KycLayer, VerificationResult> layers,
)
```

Три теста фиксируют поведение:

* без страховки — допуск **закрыт**, даже если личность подтверждена;
* MVR и криминальный фон не блокируют допуск на старте;
* оба обязательных слоя закрыты — допуск открыт.

### Stripe Identity нельзя вызывать с клиента — проверено

Перед проектированием была проведена фактическая проверка. Запрос к
`POST https://api.stripe.com/v1/identity/verification_sessions` без секретного ключа
возвращает:

```
HTTP 401
"You did not provide an API key."
```

Секретный ключ Stripe в клиентском Flutter-коде — это утечка ключа: web-сборка
раздаёт его каждому, кто откроет DevTools. Следствие: **создание сессии Identity
идёт только через Cloud Function.** В превью-режиме сервис работает в demo:

```dart
bool get isDemo => !(cloudFunctionUrl?.isNotEmpty ?? false);
```

И — важная деталь — demo-режим возвращает `pendingProvider`, а **не** `verified`.
Демо не имеет права выдавать подтверждение, которого не было. Зафиксировано тестом:

```dart
test('Identity даёт pendingProvider, а не verified', () async {
  final r = await const KycService().startIdentitySession(dateOfBirth: '');
  expect(r.status, VerificationStatus.pendingProvider);
  expect(r.status.grantsBadge, isFalse);
});
```

<a name="6"></a>
## 6. Валидаторы: юридическое обоснование каждого правила

Все валидаторы — статические чистые функции в `lib/services/validators.dart`
(371 строка). Работают офлайн, мгновенно, бесплатно. Ни один из них **не** выдаёт
`verified` с уровнем `registry` — это принципиально: формат не является
подтверждением.

Полный список:

| Метод | Строка | Проверяет | Правовая/техническая основа |
|---|---|---|---|
| `validateVin` | 29 | VIN 17 знаков | ISO 3779, контрольная цифра |
| `validateDot` | 83 | USDOT-номер | Формат FMCSA |
| `validateMc` | 112 | MC-номер | Формат FMCSA |
| `validateDealerLicense` | 158 | Дилерская лицензия | Маски по штатам |
| `validateDriverLicense` | 193 | Водительское удостоверение | Маски по штатам |
| `validateSsn` | 225 | SSN | Правила выпуска SSA |
| `validateDateOfBirth` | 282 | Дата рождения | 49 CFR §391.11 |
| `validateUsPhone` | 343 | Телефон | NANP |

### 6.1 VIN — контрольная цифра ISO 3779

Единственный валидатор, который даёт математическую гарантию. Стандарт
ISO 3779 задаёт транслитерацию букв в цифры, весовые коэффициенты по позициям
и контрольную цифру в 9-й позиции.

```dart
static const Map<String, int> _vinTranslit = { 'A':1, 'B':2, ..., 'Z':9 };
static const List<int> _vinWeights = [8,7,6,5,4,3,2,10,0,9,8,7,6,5,4,3,2];
```

Три правила:

1. **Ровно 17 символов.** Меньше — не ошибка, а «ещё не дописал» (см. ниже про UX).
2. **Буквы I, O, Q запрещены** стандартом — их путают с 1 и 0. Отдельное сообщение,
   потому что пользователь чаще всего честно скопировал их из плохого скана.
3. **Контрольная цифра**: сумма произведений транслитераций на веса по модулю 11;
   результат 10 записывается как `X`.

Важно: успешная проверка VIN даёт уровень `format`, а **не** `registry`.
Контрольная сумма означает лишь внутреннюю согласованность номера. Существование
автомобиля подтверждает только NHTSA (см. §7).

### 6.2 USDOT — почему короткий ввод не ошибка

```dart
static VerificationResult validateDot(String input) { ... }
```

Правила: только цифры, без ведущего нуля, длина до 8 знаков.

Ключевое UX-решение, зафиксированное тестом *«короткий ввод не пугает пользователя
ошибкой»*: пока введено меньше минимальной длины, статус — `idle`, а не
`invalidFormat`. Красный текст под полем в момент, когда человек набрал первую
цифру из семи, — это агрессия интерфейса, а не помощь.

Ошибка показывается, только когда ввод **не может** стать валидным при дальнейшем
наборе: появилась буква, ведущий ноль, превышена длина.

### 6.3 SSN — правила выпуска Social Security Administration

Полностью офлайновая проверка, основанная на официальных правилах выпуска SSA.
Формат `AAA-GG-SSSS`, где области никогда не выдавались при:

| Условие | Почему невалидно |
|---|---|
| area = `000` | Никогда не выпускалась |
| area = `666` | Зарезервирована и не выпускается |
| area ≥ `900` | Диапазон 900–999 не выпускается SSA |
| group = `00` | Group-номер начинается с 01 |
| serial = `0000` | Serial начинается с 0001 |
| `078-05-1120` | Легендарный демо-номер с рекламного вкладыша кошельков Woolworth 1938 г.; использовался тысячами людей, заблокирован |

Итог валидации при успехе:

```dart
// Корректный SSN уходит к провайдеру, а не подтверждается сам.
return VerificationResult.needsReview(..., tier: VerificationTier.provider);
```

Формат SSN **никогда** не даёт `verified`. Соответствие правилам выпуска означает
лишь «такой номер теоретически мог быть выдан», а не «он выдан этому человеку».
Подтвердить может только Stripe Identity / SSN-trace.

### 6.4 Дата рождения — 49 CFR §391.11

Здесь важнее всего не техника, а продуктовая трактовка закона.

**49 CFR §391.11(b)(1)** требует минимум **21 год** для межштатных коммерческих
перевозок (interstate for-hire). При этом внутриштатные перевозки в большинстве
штатов допускаются с 18 лет.

Наивная реализация отказала бы всем младше 21. Это потеря целого сегмента:
18–20-летние перегонщики — вполне рабочая аудитория для локальных заказов.
Поэтому три ветки, а не две:

```dart
if (age < 18)  return VerificationResult.invalidFormat('...');   // отказ
if (age < 21)  return VerificationResult.mismatch(               // ОГРАНИЧЕНИЕ
    'Межштатные заказы с 21 года (49 CFR §391.11). '
    'Доступны внутриштатные заказы.');
return VerificationResult.verified(...);                          // 21+
```

Статус `mismatch` выбран намеренно: это не ошибка ввода, которую надо исправить,
а факт, ограничивающий доступные заказы. Продуктовое следствие — в выдаче заказов
для такого пользователя нужен фильтр по признаку intrastate.

Дополнительно ловится **несуществующая дата**. Регулярка
`^(\d{2})[./-](\d{2})[./-](\d{4})$` пропустит `31.02.2000`; отсечение идёт через
нормализацию `DateTime`: если сконструированная дата не совпадает с введёнными
компонентами — дата не существует.

### 6.5 Телефон — NANP

North American Numbering Plan: код города (NPA) и код обмена (NXX) **не могут
начинаться с 0 или 1** — эти цифры зарезервированы для служебных префиксов.
Ведущая `1` (код страны) отбрасывается. Успешный результат нормализуется
в `(555) 233-4567`.

### 6.6 Водительское удостоверение — маски по штатам

Форматы принципиально различаются: во Флориде это буква + 12 цифр, в Калифорнии —
буква + 7 цифр, в некоторых штатах — только цифры. Реализовано таблицей масок
с обязательным параметром `state`.

**Здесь же исправлен баг продакшна** (см. §12): в существующем коде поле
водительского удостоверения принимает только цифры, что делает невозможным ввод
абсолютного большинства реальных номеров. В новой реализации разрешены буквы:

```dart
FilteringTextInputFormatter.allow(RegExp(r'[A-Za-z0-9*-]'))
```

### 6.7 Дилерская лицензия — почему всегда модерация

```dart
static const Map<String, (String, String)> dealerLicensePatterns = { ... };
```

Единого федерального реестра дилерских лицензий в США **нет** — лицензии выдают
DMV отдельных штатов, и открытых API у большинства нет. Поэтому валидатор
проверяет только маску штата, а результат — всегда `needsReview` с уровнем
`manual`. Тест фиксирует это как контракт:

```dart
test('верный формат CA уходит на модерацию, а не в verified', ...);
```

## 7. Живые проверки по реальным реестрам

Два реестра действительно проверяют существование объекта, а не формат номера.

### 7.1 NHTSA vPIC — расшифровка VIN

`lib/services/vin_service.dart` (138 строк). Публичный API, без ключа, без квот.

```
GET https://vpic.nhtsa.dot.gov/api/vehicles/DecodeVinValues/{VIN}?format=json
```

Возвращает марку, модель, год, тип кузова, завод. Автозаполнение полей карточки
автомобиля идёт отсюда — пользователю не нужно вводить то, что уже известно
государству.

Критическая деталь реализации: **решение принимается по полю `ErrorCode`,
а не по HTTP-статусу.** NHTSA отвечает `HTTP 200` даже на полностью выдуманный
VIN — просто с `ErrorCode`, отличным от `0`. Наивная проверка `if (response.statusCode == 200)`
пометила бы любой мусор как подтверждённый автомобиль.

### 7.2 FMCSA — перевозчики

`lib/services/fmcsa_service.dart` (204 строки).

```
GET https://mobile.fmcsa.dot.gov/qc/services/carriers/{DOT}?webKey={KEY}
```

Возвращает `legalName`, `dbaName`, `allowedToOperate`, `statusCode`, данные
о страховке и безопасности. Требует `webKey`, поэтому вызывается **через
Cloud Function** — ключ не должен попадать в web-сборку.

Проверяется не только существование номера, но и:

* `allowedToOperate == 'Y'` — есть ли действующее право работать;
* `statusCode == 'A'` — активен ли;
* сверка `legalName` с названием, которое ввёл пользователь → при расхождении
  `mismatch`, а не `verified`.

Для превью-режима встроена демо-база из 4 реальных DOT-номеров крупных
перевозчиков, чтобы экран можно было показать без ключа.

### 7.3 Сводная таблица источников

| Данные | Источник | Ключ | Реальная проверка существования |
|---|---|---|---|
| VIN | NHTSA vPIC | не нужен | **Да** |
| USDOT / MC | FMCSA QC | нужен | **Да** |
| Личность | Stripe Identity | секретный | **Да** |
| MVR, криминал | Checkr | секретный | **Да** |
| Дилерская лицензия | — реестра нет | — | Нет, только модерация |
| Страховой полис | — реестра нет | — | Нет, только модерация |

## 8. Cloud Functions: контракты

`functions/src/verification.ts` — 535 строк, 5 функций. Все требуют
авторизации, все имеют rate limit.

| Функция | Строка | Назначение |
|---|---|---|
| `verifyCarrierDot` | 116 | Проверка USDOT/MC в FMCSA, сверка названия, запись результата |
| `decodeVin` | 281 | Расшифровка VIN через NHTSA |
| `submitDealerLicense` | 374 | Приём дилерской лицензии на модерацию |
| `reviewVerification` | 432 | Решение модератора (admin-only) |
| `checkVerificationExpiry` | 488 | Scheduled: перепроверка истёкших подтверждений |

Три сквозных механизма.

**Единая запись результата.** Вспомогательная функция `persist()` (строка 63) —
единственное место, где пишется поддокумент `verification.*`. Клиент **никогда**
не пишет статус верификации напрямую: иначе достаточно было бы правки локального
состояния, чтобы получить бейдж.

**Rate limiting.** `assertRateLimit(uid, key, perDay)` (строка 516) — счётчик
вызовов на пользователя в сутки. Защищает и от перебора номеров, и от исчерпания
квоты FMCSA одним пользователем.

```typescript
async function assertRateLimit(uid: string, key: string, perDay: number) {
  ...
  throw new functions.https.HttpsError('resource-exhausted', ...);
}
```

**Проверка прав.** `reviewVerification` доступна только админам, иначе
`HttpsError('permission-denied')`. Все функции стартуют с проверки
`context.auth` → `HttpsError('unauthenticated', 'Требуется авторизация')`.

**Scheduled-перепроверка** нужна потому, что подтверждение — не вечное.
Перевозчика могут лишить authority; страховка истекает. `checkVerificationExpiry`
обходит просроченные записи и снимает бейдж.

> **Статус:** TypeScript написан, но **не скомпилирован** — в `functions/`
> отсутствуют `package.json` и `tsconfig.json`. Это осознанно оставлено на
> развёртывание: конфигурация зависит от плана Firebase проекта.

```dart
test('без страховки допуск закрыт — главный риск платформы', ...);
test('MVR без согласия FCRA запрещён', ...);
test('18-20 — не отказ, а ограничение внутриштатными заказами', ...);
test('корректный SSN уходит к провайдеру, а не подтверждается сам', ...);
```

<a name="12"></a>
## 12. Найденные баги в продакшн-коде

При изучении реального репозитория обнаружены три дефекта. Все — в рабочем
коде, все подтверждаются скриншотами.

### 12.1 Кнопки с текстом `?????????`

**Файл:** `app/lib/profile/edit_carrier_profile1/edit_carrier_profile1_widget.dart`

```dart
// строка 551
content: Text('?????? ?????????'),
// строка 562
text: '?????????',
```

Это не заглушки — это **потерянная кириллица** при экспорте из FlutterFlow
(строки прошли через кодировку, не поддерживающую Cyrillic). Пользователь видит
на экране «Ваши данные» кнопку с надписью `?????????`. Подтверждено скриншотом
`photo_2026-08-28_00-30-10.jpg`.

> **ИСПРАВЛЕНИЕ (внесено позже, при фактической починке бага).**
> Первоначально здесь было предположение, что кнопка означает «Удалить аккаунт».
> Это предположение оказалось **неверным**. Чтение кода показало, что обработчик
> кнопки вызывает `currentUserReference!.update(createUsersRecordData(...))` —
> то есть кнопка **сохраняет** профиль, а не удаляет аккаунт. Восстановлено как
> `'Сохранить'` (9 символов = 9 знаков `?`) и `'Данные сохранены'`
> (6 + 9 знаков = `'?????? ?????????'`). Совпадение количества символов
> подтверждает реконструкцию.
>
> Вывод для последующей работы: **не восстанавливать потерянные строки по
> смыслу окружения — только по фактическому обработчику.**

### 12.2 Валидатор номера перевозчика пропускает мусор

**Файл:** `app/lib/auth/fill_profile_carrier/fill_profile_carrier_model.dart:39-55`

Проверка — только `isEmpty` и `length < 3`. Строка `abc` проходит как номер
перевозчика. Замена — `Validators.validateDot` / `validateMc` с последующей
проверкой в FMCSA.

> **УТОЧНЕНИЕ (внесено при починке).** Масштаб бага оказался шире описанного.
> Модели дилера (`fill_profile_diller_model.dart`,
> `edit_diller_profile1_model.dart`) не имели **вообще никакой** проверки
> формата — только `isEmpty`, даже без `length < 3`. Итого исправлено
> **4 модели**, а не одна.

### 12.3 Поле водительского удостоверения физически не принимает реальные номера

**Файл:** `app/lib/auth/fill_profile_carrier/fill_profile_carrier_widget.dart:414-417`

```dart
keyboardType: TextInputType.number,
inputFormatters: [FilteringTextInputFormatter.allow(RegExp('[0-9]'))],
```

Водительские удостоверения США почти во всех штатах содержат буквы:
Калифорния — `D1234567`, Флорида — `A123456789012`. Текущий фильтр **удаляет
букву при вводе**, то есть корректный номер ввести невозможно в принципе.
Пользователь либо вводит номер без буквы (неверные данные в базе), либо
не может пройти регистрацию.

Исправление: `RegExp(r'[A-Za-z0-9-]')` + `TextInputType.text` + проверка
формата (реализовано в `Validators.validateDriverLicense`).

> **УТОЧНЕНИЕ (внесено при починке).** Здесь указан один файл, что создавало
> ложное впечатление единичного дефекта. Фактически `grep` по репозиторию нашёл
> **17 вхождений** `RegExp('[0-9]')`, из которых **8 стоят на полях документов**
> (водительское удостоверение ×4, номер перевозчика/лицензия дилера ×4) в
> четырёх экранах: `fill_profile_carrier`, `fill_profile_diller`,
> `edit_carrier_profile1`, `edit_diller_profile1`. Исправлены все 8.
> Остальные 9 вхождений (телефон ×2, дата ×1 и др.) оставлены числовыми
> **намеренно** — там фильтр корректен.

## 14. Оценка трудозатрат

Оценка из `ARCHITECTURE.md` для поддержки физлиц — **1.5–2 недели**.
После проделанной работы разбивка выглядит так:

| Блок | Состояние | Осталось |
|---|---|---|
| Модель данных, схема Firestore | **готово** | — |
| Валидаторы (8 шт.) + тесты | **готово** | — |
| Живые проверки NHTSA / FMCSA | **готово** | ключ + деплой |
| Экраны: выбор типа, KYC физлица, 3 таба | **готово** | — |
| Дизайн-токены и компоненты | **готово** | — |
| Cloud Functions (код) | **готово** | сборка + деплой: ~1 день |
| Интеграция в продакшн-приложение | — | ~2–3 дня |
| Экран модератора | — | ~2 дня |
| Вебхуки провайдеров | — | ~1 день |
| Договор со страховой | — | вне разработки |

Итого разработки осталось примерно **неделя**, при условии что вопросы
с ключами API, аккаунтами Stripe/Checkr и страховым продуктом решаются
параллельно.

### Три вывода, которые важнее кода

1. **«Проверено» — не булево.** Четыре уровня доверия и правило «бейдж даёт
   только госреестр» — единственное, что отличает настоящую верификацию от
   имитации. Всё остальное — детали реализации.

2. **Физлицо — это способ проверки, а не роль.** Решение с `carrier_kind`
   вместо третьего `UserType` сэкономило ревизию 17 ветвлений и полностью
   исключило миграцию базы.

3. **Страховка — узкое место всего направления.** Личность проверяется за $1.50
   автоматически. Страховое покрытие перегона чужого автомобиля за плату
   не проверяется никак и, скорее всего, у большинства кандидатов
   отсутствует. Это вопрос не к разработке.
